# Codebase tour

What lives where, which technologies are used and why, and how a write and a query flow through the code. Paths are relative to the repository root. For the design behind it, see `SPEC.md`; for the on-disk format, see [Architecture](/docs/architecture).

## The big picture

```text
            your code
   ┌───────────┼──────────────┬──────────────────┐
   │           │              │                  │
 timelake    Python         Rust             browser / Node / serverless
  (CLI)    (timelake-py)   (use the crate)       │
   └───────────┼──────────────┘           @timelake/client (TypeScript)
               │                                 │
        crates/timelake  (the engine)     crates/timelake-wasm (read-only)
               │                                 │
               └──────── crates/timelake-format ─┘   shared rules
                                 │
                 object storage: Iceberg metadata + Parquet files
```

- **One engine.** All writing and full SQL happen in `crates/timelake`. The CLI and the Python package are thin layers over it.
- **A second, small reader for JavaScript.** The engine depends on DataFusion and Tokio, which are too large for a browser. `crates/timelake-wasm` reimplements just the reading needed for time-series queries (latest values, time ranges, time buckets). The rules both must agree on live in `crates/timelake-format`.
- **The website** uses the client package to read the demo data, and the CLI for local SQL.

## The engine, file by file

`crates/timelake/src`, about 4,000 lines including unit tests. Read them in this order:

| File | What it does |
| --- | --- |
| `lib.rs` | The public API: `Lake`, `Table`, `Session`, options, and results, with a short example. |
| `name.rs` | `TableName`: parses and validates `namespace.table` once, at the boundary. |
| `storage.rs` | Opens the right object store for a URL (`s3://`, `gs://`, `az://`, `https://`, local). Read, write, `write_if_absent` (the conditional write), list, and delete; `Uploads`, a queue of files a commit sends all at once; also adapts the store to iceberg-rust's file interface. |
| `lake.rs` | The catalog. `Lake` is a warehouse: `create_table` writes `v1.metadata.json`, `table()` finds the current version (the head and a listing of the metadata files at once, or a check for the next version of one it already has), `tables()` lists them. |
| `table.rs` | `Table`: one version of a table (name, metadata, contract, schema) and `files()`, the live data files (from the head, or from its manifests). |
| `head/` | The head object: `mod.rs` builds it from a table, writes it after a commit without moving it backwards, and loads a table from it; `codec.rs` holds the format-neutral `HeadDoc`, the `HeadCodec` trait and the `arrow` and `json` codecs. |
| `footer.rs` | Parquet footers kept apart from their files: read from the store once, encoded for the head, decoded for scans. |
| `cache.rs` | Small bounded caches for files that never change once written (manifests, manifest lists, last-value indexes) and recently loaded table versions. |
| `schema.rs` | Fits Arrow data to a table: types Iceberg can store on create (`normalize_schema`), columns matched by name and cast on write (`align_batch`). |
| `sort.rs` | One sorting helper: sort by key columns keeping input order on ties, and keep the last row of each group. Used for writing, dedup, and the last-value index. |
| `write.rs` | Turns batches into Parquet: `sort_and_split` (sort by partition, series, time) and `PartitionWriter`, which writes sorted batches into files of the target size through the shared file writer (`timelake_format::file`: settings, columns encoded in parallel, and the statistics Iceberg records) and streams them out as multipart uploads. |
| `lvi.rs` | The last-value index: the newest row per series, merged with the previous index, read and written as Parquet. |
| `commit.rs` | The commit layer. A `SnapshotWriter` prepares manifests, the last-value index, and the manifest list, uploads them with the data files in one round, then commits the new metadata with `write_if_absent`; a lost race cleans up and retries (up to 10 times). Three kinds of change: append, replace (compaction) and delete (retention). |
| `background.rs` | Writes a call doesn't wait for (the version hint and the head), and `flush`, which waits for them before a process exits. |
| `append.rs` | `Table::append`, with inline maintenance afterwards. |
| `maintain.rs` | `Table::maintain`: retention, compaction with dedup, snapshot expiry, and file cleanup. |
| `upgrade.rs` | `Table::upgrade` (format version, missing last-value index, compaction, head; each a commit, with snapshots kept for a rollback) and `Table::rollback`. |
| `query/` | The SQL reader: `session.rs` (`Session`: parse, plan, run), `catalog.rs` (namespaces and tables for DataFusion), `provider.rs` (a table as a pruned Parquet scan or the last-value index), `dedup.rs` (dedup on read: which files may share keys, and the operator that keeps the latest write), `stats.rs` (min/max from manifests), `rewrite.rs` (latest-row queries onto the index), `route.rs` and `rollup.rs` (answering queries from rollups), `in_list.rs` (pruning with long `IN` lists), `newest.rs` (newest-first scans for `ORDER BY time DESC LIMIT`), `m4.rs` and `signal.rs` (the `m4` aggregate, and `time_weighted_mean`, `integral`, `counter_diff`, and `counter_rate`), `shared_state.rs` (one state for several of them over the same column), `series_order.rs` (reading each series in time order for those four). |
| `error.rs` | `Error`: not found, already exists, invalid input, conflict, and the underlying storage, Arrow, and Parquet errors. |

Tests live next to the code (`#[cfg(test)]` modules, with test storage in `testing.rs` that injects faults or latency) and in `crates/timelake/tests`: end to end on local disk (`lifecycle.rs`), concurrent commits (`commits.rs`), and SQL (`sql.rs`).

## Follow an append through the code

`timelake append iot.readings day1.csv`, or `t.append(batch)` in Python, ends up in `Table::append` (`append.rs`):

1. `sort_and_split` (`write.rs`): match columns to the table, compute each row's day, sort by day, series key, and time, and cut the batch into one piece per day.
2. `write_partition` (`write.rs`): encode each day's rows as Parquet under `data/time_day=…/`, several days at a time, each row group's columns on threads of their own. Each file comes back with its path, size, row count, and min/max per column; its upload waits in an `Uploads` queue (a large file's earlier parts are already sent).
3. `latest_per_series` (`lvi.rs`): the newest row of each series in the new data.
4. `commit` (`commit.rs`): a `SnapshotWriter` prepares a manifest for the new files, the merged last-value index, and the manifest list, then uploads them and the data files at once. With more than eight manifests, the old ones are merged into one so reads stay quick.
5. `publish` (`commit.rs`): `write_if_absent(vN+1.metadata.json)`. If the file already exists, another writer won: delete every file this attempt wrote, reload, and retry. On success, update `version-hint.text` and the head in the background (`background.rs`, `head/`).
6. Back in `append`: if inline maintenance is on, run size-tiered compaction on the days this append touched, and expire old snapshots in batches. If that fails, the append still succeeded: the error is returned in the result, not raised.

## Follow a query through the code

`timelake sql "…"` or `lake.sql("…")` calls `Session::sql` (`query/session.rs`):

1. Parse the SQL and find every table it mentions.
2. `prefetch`: load all those tables in parallel. A table with a head comes from that one object (metadata, files, last-value index, footers), confirmed by a listing made at the same time. A table this process already has is checked for a newer version while planning goes on; the scan waits for that check. Others are read through the metadata chain.
3. DataFusion plans the query. It asks the lake catalog (`query/catalog.rs`) for each table and gets a `TimelakeProvider` (`query/provider.rs`).
4. The optimizer runs Timelake's rules. The latest-row rewrite (`query/rewrite.rs`): if the query asks for the newest row per series (or the newest row for some series), the table scan is replaced with a scan of the last-value index. Rollup routing (`query/route.rs`): a `GROUP BY time_bucket` answered from a rollup for the buckets it has right. Newest-first (`query/newest.rs`): `ORDER BY time DESC LIMIT k` reads time partitions newest first and stops early. Series order (`query/series_order.rs`): scans under a `time_weighted_mean` merge files that could give a series out of order.
5. Otherwise the provider drops files whose min/max values (`query/stats.rs`) can't match the `WHERE` clause, spreads the remaining files over parallel scan tasks, fetches every file footer once, and hands the files to DataFusion's Parquet reader, which skips row groups and pages. For `IN` lists longer than DataFusion prunes with, the provider works out the row groups and pages to read from the footers itself (`query/in_list.rs`) and passes them as each file's access plan. On scans without filter pushdown, a predicate adapter does the same for a join's runtime filter as each file is opened. With dedup on, files of one partition whose key bounds overlap may hold the same `(series, time)` (`query/dedup.rs`): they are pruned only on the key columns, split by a hash of the series, merged in key order slice by slice, and only the latest write of each key is kept.
6. DataFusion runs the rest (filters, joins, aggregates) and returns Arrow batches.

## The CLI and the Python package

- `crates/timelake-cli/src`: `main.rs` defines the commands with `clap` and prints results as a table, CSV, or JSON; `load.rs` reads CSV and Parquet and appends them in commits; `info.rs` renders `timelake info` as text or JSON; `bench.rs` is the hidden benchmark mode of `timelake sql`. `tests/cli.rs` runs the binary end to end.
- `crates/timelake-py/src/lib.rs`: classes `Lake` and `Table`. Each method runs the engine on a shared Tokio runtime and releases Python's GIL while it waits. Data comes in through the Arrow C stream interface, so pyarrow and polars objects work directly. Errors map to `KeyError`, `FileExistsError`, `ValueError` and `timelake.ConflictError`.
- `crates/timelake-py/python/timelake`: the Python side: `__init__.py`, the type stub `_timelake.pyi`, `_types.py` (typed result dicts), and `py.typed`. Tests are in `crates/timelake-py/tests`.

## The WebAssembly reader and the TypeScript client

The WASM module never makes network requests. The TypeScript client fetches bytes and hands them in, which keeps the module small and identical in every JavaScript runtime:

1. The client fetches `version-hint.text` and `vN.metadata.json`; `new Table(json)` parses it (`meta.rs`).
2. The client fetches the manifest list and manifests; the module parses them (Avro) into a list of files.
3. `planFiles(query)` drops files whose min/max values can't match (`prune.rs`).
4. For each file, the client fetches the end of the file (the footer). `ParquetFile.plan` (`file.rs`) returns the byte ranges of the row groups and columns needed. The client fetches just those ranges.
5. `Query.push` decodes and filters each file (`filter.rs`) and collects rows, time buckets (`aggregate.rs`), or the newest row per series (`latest.rs`); `finish` returns JSON rows (`output.rs`). The client validates them with Zod if a schema was given.

`spec.rs` describes the query a host sends; `error.rs` the errors it gets back. The crate has its own unit tests and a golden test on a small table written by the engine (`crates/timelake-wasm/tests`).

`packages/timelake-client/scripts/build-wasm.sh` compiles the crate, shrinks it with `wasm-opt`, and embeds it as base64 in `src/wasm/inline.js`, so the package loads without a separate `.wasm` file. The generated files are committed with a hash of their sources in the header; `bun run check:wasm` (and CI) fails when they are stale. The client's tests build a small warehouse with the CLI, serve it locally, and compare answers with the engine's, without network access.

## The website

| Path | What |
| --- | --- |
| `dashboard/app/(site)` | Landing page, `/docs` (one folder per page), and `/benchmarks`. |
| `dashboard/app/(app)/explore` | The Explorer: tables, a table's details and latest values, a series chart, a SQL console. |

| `dashboard/lib/lake` | The Explorer's data layer, with two backends behind one interface: `wasm.ts` reads a public warehouse with `@timelake/client` (used on timelake.dev, no SQL), `cli.ts` runs the `timelake` binary (local, full SQL). `index.ts` picks one by environment variable. |

| `dashboard/components` | Page pieces (diagrams, charts, tables); `components/ui` holds shadcn/ui components. |

Vercel builds and deploys the site on every push to `main` (project root `dashboard/`). The demo data on timelake.dev is a small warehouse on Vercel Blob, built by `scripts/build-demo-warehouse.sh` and uploaded with `bun run upload-demo`.
