# TypeScript client

`@timelake/client` reads Timelake tables over HTTPS from the browser, Node, Bun, or serverless functions, and appends to them from the same places ([Writing](#writing)). A WebAssembly build of Timelake's reader (`crates/timelake-wasm`) parses the Iceberg metadata, prunes files and row groups, decodes Parquet, and computes aggregates. The package only fetches the byte ranges the reader asks for. There is no server and no query engine to run. Rows can be validated and typed with Zod.

```ts
import { z } from "zod"
import { Lake } from "@timelake/client"

const Reading = z.object({
  time: z.coerce.date(),          // times arrive as ISO strings
  tags_id: z.number().int(),
  velocity: z.number().nullable(),
})

const lake = new Lake("https://<store>.public.blob.vercel-storage.com/demo")
const readings = lake.table("tsbs.readings", Reading)

await readings.latest({ series: [1, 2, 3] })        // newest row per truck (last-value index)
await readings.range({ series: 7, from: "2026-01-03T12:00:00Z", to: "2026-01-03T13:00:00Z" })
const hourly = await readings.bucket({
  series: 7, every: "1h",
  agg: { velocity: ["avg", "max"], "*": ["count"] },
})
hourly[0].velocity_avg                               // number | null, typed from the agg map
```

## Install

```bash
npm install @timelake/client zod
```

It needs `zod` 4 as a peer dependency. Inside this repository it is a bun workspace package, and the website imports its TypeScript source.

## What it reads

A warehouse served over plain HTTP(S), such as Vercel Blob, a public S3, R2 or GCS bucket, or a CDN. The server must support `Range` requests (it then answers `206`); without them the client downloads whole files and still returns correct results. A plain HTTP server can't list files, so the client finds tables through the warehouse's `timelake-tables.json`, which the writer maintains (`timelake index` rewrites it).

## API

| Call | Returns |
| --- | --- |
| `new Lake(url, { fetch?, concurrency?, cacheMs?, rewriteUrl? })` | A warehouse handle. `concurrency` caps parallel requests (default 16). `cacheMs` controls how long a loaded table version is reused (default 5000). `rewriteUrl` maps object URLs when a warehouse has moved. |
| `lake.tables()` | `string[]` of `namespace.table`. |
| `lake.table(name, schema?)` | A table handle. Rows are typed and validated with the Zod schema if one is given; otherwise they are `Record<string, unknown>`. |
| `table.latest({ series?, columns? })` | The newest row of each series, read from the last-value index in a single request. Throws if the table has no index. |
| `table.range({ series?, from?, to?, columns?, limit?, order? })` | Rows in `[from, to)`, ordered by time. `columns` narrows the result type to those columns. |
| `table.bucket({ series?, from?, to?, every, agg, by? })` | One row per bucket (and per `by` value): `bucket: Date` plus `<column>_<op>` for each aggregate (`count`, `sum`, `avg`, `min`, `max`, `first`, `last`); `"*": ["count"]` gives `count`. |
| `table.info()` | Contract, schema, snapshots, and live files of the current version. |
| `table.zodSource()` | The TypeScript source of a Zod schema for the table, ready to paste. |
| `table.refresh()` | Forget the cached table version, so the next query reads the newest one. |
| `zodSource(info, exportName?)`, `readerVersion()` | Standalone exports: generate Zod source from a `table.info()` result; the version of the embedded WASM reader. |
| `table.lastStats` | Requests, bytes, files, and milliseconds of the last query. |

`series` is a value or a list of values of the first series-key column, or an object such as `{ device_id: ["a", "b"] }`. Times are `Date` objects, ISO strings, or epoch milliseconds. Durations are written like `500ms`, `30s`, `10m`, `1h`, `1d` or `1w`, or given as a number of milliseconds. Buckets are aligned to the Unix epoch.

## Writing

`TableWriter` appends to a table from JavaScript: a Cloudflare Worker, Node, Deno, Bun, or a browser. The WebAssembly module runs the engine's write path. It aligns rows to the table's schema, adds the insertion time, sorts by series and time, keeps the last of rows with the same series and time, and writes one Parquet file per time partition. Then it commits the way the engine does, and updates the last-value index and the head. The engine, DuckDB, and the reader above see the rows like any others.

```ts
import wasm from "@timelake/client/timelake.wasm"
import { TableWriter, initWasm, r2Store } from "@timelake/client/workers"

initWasm(wasm)

export default {
  async queue(batch, env) {
    // An R2 binding LAKE on the bucket that holds s3://my-bucket/lake.
    const writer = new TableWriter(r2Store(env.LAKE), "s3://my-bucket/lake", "iot.readings")
    const rows = batch.messages.map((m) => m.body)          // { time, device, temp }
    await writer.append(rows, { batchId: batch.messages[0].id })
  },
}
```

- **In Workers**, import from `@timelake/client/workers`, and pass the module from `@timelake/client/timelake.wasm` to `initWasm`. Workers can't compile WebAssembly from bytes at runtime, so the default entry, which embeds the module as base64, doesn't run there. Wrangler bundles the `.wasm` import as a compiled module. Elsewhere (Node, Deno, Bun, browsers), the default `@timelake/client` works as is.

- **Store.** A writer reads and writes objects through a `Store`: `r2Store` for an R2 binding, `memoryStore` for tests, or your own (`get`, `getRange`, `put`, `putIfAbsent`, `list`, `delete`, and optionally `upload` for multipart uploads). `putIfAbsent` must be atomic, because commits rely on it. The second argument is the warehouse root as the table metadata records it. Keys are what follows the bucket.
- **Rows.** Pass objects or an Arrow IPC stream. In objects, times are `Date`s, ISO strings, or epoch milliseconds (millisecond precision). Use Arrow IPC for microseconds. Integers beyond 2^53 are written exactly as `bigint`s; runtimes without `JSON.rawJSON` (ES2025) reject such a `bigint` instead of rounding it. A column the table doesn't have, or a missing required one, is an error, and nothing is written.
- **Commits.** A writer keeps the version it last committed, so a steady writer doesn't reload the table before each append. If another writer committed in between, the commit reloads and retries. A `batchId` makes retries safe: an append whose batch id is already in the table is skipped.
- **One writer per table works best:** a Queues consumer or a Durable Object that collects rows into appends of a few thousand or more. Concurrent writers are safe, but each conflict costs a retry, and many small appends make many small files.
- **Creating tables.** Create the table first with the CLI or Python. Writers can't create tables yet.
- **Memory and time** in workerd (Cloudflare's runtime, run locally with Miniflare on a local R2 bucket; TSBS-like rows with 9 columns):

| | Time | WebAssembly memory |
| --- | ---: | ---: |
| Append of 1,000 rows | 0.2 s | 5 MiB |
| Append of 100,000 rows | 0.7 s | 37 MiB |
| 60 appends of 1,000 rows with inline maintenance | 18 ms each (median), 0.2 s with compaction | 16 MiB |
| Compaction of a day of 24 files (1.2M rows, 47 MiB) | 2.7 s | 95 MiB |

  A Worker has 128 MB of memory, WebAssembly included. Compaction reads each file a window of pages at a time, merges at most 24 files at once (larger groups in parts), and writes row groups of at most 16 MiB. Files written from JavaScript have data pages of 8,192 rows (the setting `data-page-rows`; the engine writes 20,000), since compaction holds a page per column of each file it merges. Method and details: [`bench/results/WORKERS.md`](https://github.com/polythings/timelake/blob/main/bench/results/WORKERS.md).
- **Maintenance.** After each append, the writer runs what the engine runs inline. It merges size tiers of small files in the partitions the append touched, and rewrites cold partitions whole. It also applies retention and expires snapshots in batches. Compaction is a streaming merge: memory is about one row group per file being merged, not the partition. One append's compaction reads at most `maxCompactBytes` (default 64 MiB), so it stays within a request's CPU time; what's left waits for the next append. `writer.maintain({ maxBytes })` runs a full pass, for example from a scheduled Worker. `timelake maintain` elsewhere is optional.

## How a query runs

1. Read the table's head object (`metadata/timelake-head`) and `version-hint.text` at the same time. The head holds the metadata, the files, and usually the last-value index and file footers, so a `latest` query needs no further request. A HEAD request for the next version runs alongside the query; if one exists, the result is dropped and the query reruns on the newest version. Tables without a head are read through the metadata, the manifest list, and the manifests. A loaded version is reused for `cacheMs`, and after that only checked for a newer one.
2. Prune data files on their Iceberg column bounds (time range, series key).
3. For each remaining file, take the Parquet footer from the head or fetch it, then fetch only the row groups and columns the query needs.
4. Decode, filter, and sort or aggregate in WebAssembly, and return JSON rows (validated with Zod if given).

## Limits

- Writes are appends to existing tables (see [Writing](#writing)); creating tables and schema changes go through the CLI, the Python package, or the Rust library.
- It answers time-series query shapes, not arbitrary SQL. For SQL, use the engine (CLI, Python) or plain DuckDB.
- The WASM module is embedded as base64, about 8 MB of JavaScript (about 2 MB gzipped). That is fine on servers; in browsers, load it lazily.
- Pruning works at the row-group level. Tables meant for web reads should use smaller row groups (the demo uses `timelake.row-group-rows=65536`).
