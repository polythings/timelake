# Real S3 results (2026-10-13)

> **Run:** `run_aws.sh` from a laptop (M1 Pro) to S3 in us-east-2 over the internet: about 45 ms to connect and 130 ms to the first byte. Absolute latencies include that trip. Request counts, bytes and request cost don't depend on where the client runs, and every system takes the same path.
> **Data and queries:** TSBS IoT, 500 trucks × 3 days, the same as Phase 0 ([BASELINE.md](BASELINE.md), [v0/README.md](../v0/README.md)). Phase 0 suites use the sorted layout.
> **Requests:** counted by `tools/s3proxy` in AWS mode. Cost uses S3 list prices for us-east-2: $0.0004 per 1,000 GET/HEAD and $0.005 per 1,000 PUT/POST/LIST.
> **First** = first run in a fresh process; **best** = best of 3 repeats in the same process. Geometric means, in seconds.
> **Versions:** DuckDB 1.5.6, DataFusion 54.1 (Python) / 55 (Rust), Polars 2.0, PyIceberg 0.12, Lance 13, Timelake at this commit.

## Key findings

1. **Freshly written tables are where naive lakes fail on S3.** TSBS queries on the first run, right after 1,728 five-minute commits:

   | System | seconds per query | requests per query | $ per 1M queries (requests at GET price) |
   |---|---:|---:|---:|
   | **Timelake** (its reader) | **1.5** | **65** | **26** |
   | Lance | 3.3 | 2,810 | 1,124 |
   | Iceberg, PyIceberg appends | 20.4 | 1,522 | 609 |
   | S3 Tables, PyIceberg appends | 21.6 | 1,547 | 619 |

   Timelake compacts as it writes (235 small compactions during ingest), so readers see 286 files instead of 1,560–1,729. Single-truck queries show the same: 1.3 s for Timelake vs 9.5 s for S3 Tables.

2. **S3 Tables fixes the layout, but hours later.** Its managed compaction ran **2.4–2.6 hours** after ingest ended. Until then, every reader pays the 20 s queries above. After it ran (7 files), TSBS queries took 2.4 s and single-truck queries 6.7 s; Timelake took 1.2 s and 1.0 s. Compaction itself was cheap here: about 300 MB at $0.005/GB plus $0.002 per 1,000 objects.

3. **Timelake commits fastest.** Median commit 0.48 s (Timelake) vs 0.99 s (Lance), 1.46 s (S3 Tables) and 2.41 s (Iceberg with a SQL catalog), for the same 1,728 commits. Timelake's p95 (2.0 s) is the inline compaction. PyIceberg commits slow down as the table grows, because each one rewrites the manifest list.

4. **Plain DuckDB over Timelake tables works but is slower than Timelake's reader** (2.7–3.0 s vs 1.2–1.5 s on TSBS). Right after ingest it still makes 17× fewer requests than DuckDB over naive Iceberg (89 vs 1,522 per TSBS query).

5. **Over S3, first runs are 9–24× slower than local disk for every engine** (Phase 0 suites). About 24–32 requests and 28–40 MB per TSBS query; request cost $10–13 per 1M queries. DuckDB's cache brings repeats down to 0.44 s; DataFusion and Polars don't cache, so repeats stay near first-run speed. → Timelake needs its reader cache ([spec 44](../../spec/0044-timebench.md)).

6. **S3 Tables isn't conflict-free for a single writer.** Two of 1,728 PyIceberg commits failed with "concurrent update", most likely against S3 Tables' own maintenance, and were retried. PyIceberg then couldn't delete its orphaned files: S3 Tables doesn't let clients delete objects.

7. **S3 Express One Zone (tested separately with every client library):** Lance 13 reads stale versions there: it finds the latest version by listing order, and S3 Express listings are unsorted. Timelake read correctly. S3 Express also rejects list prefixes that don't end in `/`.

## Caveats
- Five v0 queries on S3 failed when S3 reset connections under many parallel reads, before the proxy retried dropped reads: four on naive Iceberg (ingested) and DuckDB `last-loc` over Timelake (ingested). They're left out of the means for those engines.
- S3 Tables' object count isn't reported: table buckets can't be listed.
- TPC-H and ClickBench weren't run over the internet; they scan hundreds of MB per query.
